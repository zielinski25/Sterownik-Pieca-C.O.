# Audyt bezpieczeństwa, prywatności, zasobów i baterii — Android

**Data:** 2026-10-10  
**Wersja źródeł:** Android `v0.31.0`, `minSdk 26`, `targetSdk 35`; projekt w katalogu `android/`.  
**Zakres:** statyczny przegląd manifestu, reguł kopii zapasowych, preferencji i Keystore, klienta RTDB/HTTP, serwisu alarmowego, powiadomień, cyklu aktywności, pogody i konfiguracji Gradle. Nie audytowano reguł RTDB/Firebase wdrożonych w konsoli ani pełnego firmware ESP32.

## Wniosek w skrócie

Nie znalazłem kodu analityki reklamowej ani jawnego wysyłania tokenów do loggera aplikacji. Znalazłem jednak istotne granice bezpieczeństwa: wariant `debug` nie jest odizolowany od sterownika produkcyjnego, wspólny token poleceń znajduje się w kliencie, a lokalne API ESP32 przenosi hasła przez nieszyfrowane HTTP. Dodałem ograniczenia adresów i przekierowań, szyfrowanie lokalnej kopii Telegrama, wyłączenie kopii zapasowych, oszczędniejsze odpytywanie UI i wybrany debugowy znak graficzny. Te zmiany **nie** usuwają potrzeby sprawdzenia reguł Firebase ani zabezpieczenia firmware.

„Zero wycieków” i „zero zużycia baterii” nie da się potwierdzić z samego kodu. Długotrwały foreground service utrzymujący monitoring alarmów ma koszt energetyczny i zależy od Androida, sieci oraz ograniczeń producenta telefonu.

## Ustalenia według ryzyka

| Poziom | Ustalenie i dowód w kodzie | Status / ograniczenie |
|---|---|---|
| **Wysoki — bezpieczeństwo sterownika** | Ikona, nazwa i powiadomienie `TEST` nie tworzą środowiska symulacyjnego. Wariant debug ma inny `applicationId`, ale korzysta z tego samego adresu RTDB, domyślnego tokenu poleceń i ścieżki `/piec/cmd.json`; klient zawiera metodę wysyłania poleceń. Nie widać bramki `BuildConfig.DEBUG`, która blokowałaby zapis, OTA lub sterowanie. | **Nie zmieniałem tego automatycznie** — pełne zablokowanie poleceń w debug może zmienić zamierzone testy, a prawdziwa izolacja wymaga osobnej bazy i poświadczeń. Dopóki nie ma osobnego backendu/read-only guard, traktuj APK `TEST` jako aplikację mogącą komunikować się z tym samym sterownikiem. Oznaczenie wizualne nie oznacza „bezpieczny symulator”. Nie wykonywałem żadnych poleceń ani testów na piecu. |
| **Wysoki, warunkowy — autoryzacja poleceń** | `Prefs.DEFAULT_CMD_TOKEN` jest wartością kompilowaną do klienta, a `Rtdb.sendCommand()` dołącza ją do zapisu polecenia. Token w APK można odzyskać; `isMinifyEnabled=false` nie zapewnia ukrycia sekretów. | Jeżeli token jest jedyną kontrolą po stronie firmware/RTDB, należy traktować go jako ujawniony. Faktycznego wpływu nie da się rozstrzygnąć bez reguł RTDB i kodu weryfikującego token w firmware. Zalecane są reguły per użytkownik/rola i walidacja po stronie zaufanego backendu; ewentualna rotacja musi być skoordynowana z firmware. Nie zmieniałem wspólnego tokenu, bo mogłoby to odciąć działającą instalację. |
| **Wysoki — dane uwierzytelniające w sieci lokalnej** | `wifiAdd()` wysyła hasło Wi-Fi w JSON, a `tgSave()` przekazuje token bota do centrali. Te endpointy używają HTTP; manifest i konfiguracja sieci dopuszczają cleartext. | **Częściowo ograniczone w patchu:** klient akceptuje wyłącznie literalne prywatne IPv4 z zakresów RFC1918 i bezpieczną ścieżkę; osobny klient lokalny nie podąża za przekierowaniami ani nie ponawia POST. Zmniejsza to ryzyko wysłania danych do publicznego hosta przez złośliwe/stare `ip` lub skonfigurowany proxy albo redirect 307/308. Nadal nie ma szyfrowania ani uwierzytelnienia HTTP między telefonem i ESP — osoba w tej samej sieci może przechwycić lub podrobić ruch. Docelowo potrzebne jest TLS i uwierzytelnienie lokalnego API w firmware. |
| **Średni — token Firebase w URL** | RTDB REST używa `?auth=<ID_TOKEN>`. Firebase opisuje ten sposób jako metodę dla Firebase ID tokenów; w tej samej dokumentacji nagłówek Bearer jest opisany dla Google OAuth2 access tokenów. Dlatego nie zamieniłem tego mechanicznie na `Authorization: Bearer` — mogłoby to zepsuć autoryzację i monitoring [1](https://firebase.google.com/docs/database/rest/auth). | Żądania idą po HTTPS i nie znaleziono interceptorów logujących URL-e. Tokeny w query są jednak bardziej podatne na zapis w logach serwerów/proxy/diagnostyce niż nagłówki. Nie logować pełnych URL-i i nie przekazywać ich do raportów. Ewentualną zmianę transportu testować na RTDB testowym. |
| **Średni — prywatność na ekranie blokady** | Kanał alarmu ma `VISIBILITY_PUBLIC`; powiadomienie zawiera `info.msg`, które może ujawnić typ alarmu, wartość ADC dymu lub temperaturę kotła. To zamierzona, użyteczna funkcja alarmowa, ale pokazuje szczegóły osobie postronnej. | Pozostawiłem widoczność alarmu, ponieważ jej zmiana pogarszałaby czytelność alarmu na zablokowanym telefonie i kanały Androida są trwałe po utworzeniu. Można rozważyć prywatne powiadomienie z ogólnym tekstem publicznym; istniejące kanały wymagałyby osobnej migracji/testu. |
| **Średni — tokeny Firebase w pamięci CE** | ID token i refresh token są zapisywane w app-private SharedPreferences w credential-encrypted storage; kopia device-protected używana w Direct Boot jest osobno AES-GCM. Aplikacyjna warstwa CE nie szyfruje tych dwóch wartości. | Sandbox aplikacji i szyfrowanie plików Androida ograniczają typowy dostęp; po wyłączeniu backupu nie powinny trafiać do standardowej kopii. Na zrootowanym/skompro­mitowanym telefonie po odblokowaniu nadal należy traktować je jako możliwe do odzyskania. Dalsze szyfrowanie CE byłoby obroną warstwową, ale wymaga ostrożnej migracji istniejących sesji i testów Direct Boot. |
| **Średni — lokalizacja pogodowa** | Aplikacja wysyła zapisane współrzędne `latitude`/`longitude` do `api.open-meteo.com` przez HTTPS przy pobraniu prognozy. Nie prosi o uprawnienie GPS; współrzędne pochodzą z ustawień aplikacji. | To jawny, funkcjonalny przepływ danych do zewnętrznego dostawcy, nie ukryty odczyt lokalizacji. Wartość może wskazywać dom. Połączone wywołania startowe zostały zserializowane, aby uniknąć równoległego duplikatu. |
| **Średni — koszt monitoringu w tle** | Gdy monitoring jest włączony i istnieje sesja, `AlarmMonitorService` utrzymuje SSE, wykonuje awaryjny GET co 30 s oraz rozpoczyna strumień ponownie co 3 min (wraz z początkowym GET). Przy stabilnej sieci daje to około **120 fallback GET/h + 20 GET/h przy reconnectach**, oprócz SSE. | Fallback jest celowy: wykrywa strumień, który pozostaje otwarty, lecz przestał dostarczać zmiany. Nie usuwałem go bez testu niezawodności alarmu. W foreground polling UI zmniejszyłem z 4 s do 8 s — około **900 → 450 GET/h** podczas aktywnego ekranu; przy włączonym serwisie obie ścieżki nadal działają równolegle. To szacunki z interwałów, nie pomiar baterii. |
| **Niski/średni — dawny fallback hasła** | W źródle była nieużywana deklaracja `DEFAULT_FB_PASS`; nie znaleziono jej wywołań. Stała może być widoczna w starym źródle/artefakcie, nawet jeśli ta aplikacja jej nie używała. | Usunąłem ją z lokalnego źródła. W dostarczonym patchu nie powielam jej wartości: osobny skrypt PowerShell usuwa deklarację po nazwie. Usunięcie ze źródła nie unieważnia starych APK ani historii; jeżeli było to prawdziwe hasło, należy je zmienić poza aplikacją. |
| **Niski/średni — integralność łańcucha budowania** | Wersje bezpośrednie są przypięte, ale nie ma `gradle/verification-metadata.xml` ani lockfile; wrapper wskazuje Gradle 8.9 i nie ma przypiętego checksumu dystrybucji. Wersje AGP/Kotlin/AndroidX/OkHttp są starszym zestawem (np. OkHttp 4.12.0), nie przeprowadzono skanowania CVE/SCA. | Nie stwierdzam podatności w konkretnej zależności. Zalecane jest wygenerowanie i sprawdzenie metadanych weryfikacji po rozwiązaniu zależności na komputerze z JDK; Gradle opisuje tę kontrolę w [1](https://docs.gradle.org/current/userguide/dependency_verification.html). Aktualizację AGP/Gradle/OkHttp rób jako zestaw i testuj na telefonie, zamiast podnosić sam wrapper. |

## Co zmieniłem

- Zintegrowałem wybrany **wariant kolorystyczny nr 2** jako debugowy adaptive icon. Tło bitmapowe, przezroczysty foreground i osobny monochromatyczny wektor TEST. Zmiany są wyłącznie w `src/debug/`; produkcyjne `src/main/res/mipmap-anydpi-v26/ic_launcher*.xml` oraz produkcyjny foreground/background pozostały nietknięte.
- Wyłączyłem backup aplikacji (`allowBackup=false`) i jawnie wykluczyłem domeny CE/DE zarówno z cloud backup, jak i device transfer. Android dokumentuje, że na części OEM samo `allowBackup=false` może nie wyłączyć transferu urządzenie–urządzenie, dlatego pozostawiłem jawne reguły obu ścieżek: [2](https://developer.android.com/identity/data/autobackup).
- Telegram bot token i chat ID są teraz odczytywane/zapisywane przez istniejący AES-GCM + Android Keystore (`getSecret`/`setSecret`); stare wartości tekstowe są migrowane przy odczycie. Przy błędzie szyfrowania lokalna wartość jest usuwana, a UI informuje o problemie.
- Zabezpieczyłem lokalne żądania ESP przed hostami publicznymi, niebezpiecznymi ścieżkami, systemowym proxy i przekierowaniami. Pozostaje jawny cleartext na lokalnym Wi-Fi.
- Usuniłem adres e-mail z bufora kopiowalnych logów logowania.
- Po wylogowaniu polling UI nie odpytuje RTDB bez refresh tokenu; pogodowe żądania startowe są serializowane; interwał odświeżania UI wynosi 8 s. Ekran może więc odświeżyć temperaturę do 4 s później niż wcześniej.
- Tekst ustawień baterii informuje, że wyjątek optymalizacji jest opcjonalny i może zwiększyć pobór energii. Aplikacja nie wyłącza tej optymalizacji automatycznie.

## Kontrola zasobów i cyklu życia

W statycznym przeglądzie nie znalazłem oczywistego, nieograniczonego wycieku: klienty OkHttp są współdzielone, streaming call jest anulowany po anulowaniu coroutine, scope usługi jest anulowany w `onDestroy`, `MediaPlayer` jest zatrzymywany/zwalniany, a dynamiczne receivery aktywności są wyrejestrowywane. Alarm audio używa wake mode tylko podczas odtwarzania dźwięku — to oczekiwane zachowanie alarmu.

## Wykonane kontrole i granice audytu

- XML: **25 plików** zasobów parsują się poprawnie.
- Ikona: finalny debug asset ma **512×512**; przygotowałem podgląd kołowej maski. XML produkcyjnej ikony porównałem z bazą — bez zmian.
- Oba patche przechodzą `git apply --check --unidiff-zero` na odpowiednich stanach bazowych; po zastosowaniu jedyną różnicą do źródła jest usuwana przez skrypt deklaracja `DEFAULT_FB_PASS`.
- Dodałem testy jednostkowe allowlisty prywatnego IPv4 i bezpiecznych ścieżek, ale **nie uruchomiłem** `:app:testDebugUnitTest` ani `:app:assembleDebug`: w tym środowisku nie ma JDK/`java`. Patch wymaga lokalnego buildu przed instalacją.
- Nie wykonano dynamicznego przechwytywania ruchu, testu z APK, audytu reguł Firebase w konsoli ani pomiaru baterii. Nie ma twierdzenia, że aktualne zmiany działają runtime.
- Nie wykonywałem instalacji, rebootu, symulacji alarmu, poleceń, OTA ani żadnej operacji na żywym piecu; firmware nie był budowany ani flashowany.

## Zalecana kolejność dalszych działań

1. Zastosuj odpowiedni patch zgodnie z `ANDROID-SECURITY-BATTERY-README.md` i uruchom lokalnie `:app:testDebugUnitTest :app:assembleDebug`. Jeżeli `git apply --check` nie przechodzi — zatrzymaj się, bez `--reject`.
2. Zanim debug APK zostanie uznany za bezpieczny test, rozdziel RTDB/poświadczenia albo dodaj read-only guard dla komend/OTA. Nie używaj etykiety `TEST` jako dowodu, że backend jest testowy.
3. Poza aplikacją sprawdź reguły RTDB i traktuj wspólny token komend oraz dawny fallback hasła jako potencjalnie ujawnione; rotację planuj razem z firmware/backendem.
4. Zabezpiecz API ESP32 TLS + uwierzytelnieniem. Sam filtr RFC1918 chroni przed częścią błędnych/publicznych celów, nie przed podsłuchem w LAN ani innym hostem prywatnym.
5. Nie wyłączaj optymalizacji baterii rutynowo. Jeżeli monitoring ma być stale aktywny, zaakceptuj większy pobór i obserwuj raport świeżości; Android/OEM nadal mogą przerwać usługę lub opóźnić sieć.
